# Data model

Türkçe: [../tr/veri-modeli.md](../tr/veri-modeli.md)

After the Phase 1 discovery we added two things to the `outage` table from the plan: the source's own id (`external_id`) and coordinates (`lat`, `lon`). Both are nullable because not every source provides them. The table will be written as a Flyway migration in Phase 3; this page describes it.

## outage table

| Column | Type | Null | Description |
|---|---|---|---|
| `id` | uuid | no | Primary key, generated by the api |
| `source` | varchar(32) | no | `BEDAS`, `ISKI`, ... |
| `external_id` | varchar(64) | yes | The source's own record id. CK planned (BEDAŞ/AEDAŞ/ÇEDAŞ): `plannedOutage.id`, or `id/DISTRICT` if the record spans several districts. CK faults: `OUTAGE_NO/DISTRICT`. Null if the source has no id (KCETAŞ, İZSU, İSKİ). Why: [02-collector.md](02-collector.md) |
| `type` | varchar(16) | no | `ELECTRICITY`, `WATER`, `GAS` |
| `planned` | boolean | no | Planned or fault |
| `il` | varchar(64) | no | Normalized province name |
| `ilce` | varchar(64) | no | Normalized district name |
| `mahalleler` | text[] | no | Normalized neighbourhood list, may be empty |
| `starts_at` | timestamptz | no | Start |
| `ends_at` | timestamptz | yes | Estimated end; null if the source doesn't give one |
| `reason` | text | yes | Reason/description from the source |
| `source_url` | text | no | Link to the original announcement |
| `lat` | double precision | yes | Latitude if the source provides coordinates |
| `lon` | double precision | yes | Longitude if the source provides coordinates |
| `dedup_key` | varchar(128) | no | Deduplication key, unique |
| `first_seen_at` | timestamptz | no | Scan where it was first seen |
| `last_seen_at` | timestamptz | no | Scan where it was last seen |

`lat` and `lon` are either both set or both null (check constraint).

## Deduplication

The same outage comes back on every scan. `dedup_key` decides which row is which outage:

- If `external_id` is set: `dedup_key = <source>:<external_id>`, for example `BEDAS:36876717`.
- If `external_id` is null: `dedup_key = <source>:h:<sha256>`. The hash input is the source, the normalized district, `starts_at` (UTC, ISO-8601) and the alphabetically sorted normalized neighbourhood list, joined with `|`.

Why one column: the upsert goes through a single unique index (`ON CONFLICT (dedup_key)`), so we don't write two separate upserts for the two cases. We still want an extra guarantee for the source id:

```sql
create unique index outage_dedup_key_uq on outage (dedup_key);
create unique index outage_source_external_id_uq on outage (source, external_id)
  where external_id is not null;
```

The hash path has a weakness: if the source changes the start time or the neighbourhood list, the same outage looks like a new record and the old one becomes `GONE` after a while. Sources with ids don't have this problem, which is why the id is preferred.

## Change detection in the collector

The collector writes to a Redis Stream, not to the database. It keeps a hash of each record's content (`content_hash`) and compares it with the previous scan. The record's identity still comes from the `dedup_key` rule above; `content_hash` only answers "did it change":

- new `dedup_key` -> `NEW`
- same `dedup_key`, different `content_hash` -> `UPDATED`
- present in the previous scan, missing in this one -> `GONE`

## Active outage

`starts_at <= now()` and (`ends_at` is null or `ends_at > now()`). Records that disappeared from the source (`GONE`) but whose end time hasn't come yet are not deleted; they are tracked with `last_seen_at`. How they count in the map summary is decided in Phase 3.

## Indexes (Phase 3)

- `(type, il, ilce)`: for the filtered list and the map summary
- `(starts_at, ends_at)`: for the active outage query
